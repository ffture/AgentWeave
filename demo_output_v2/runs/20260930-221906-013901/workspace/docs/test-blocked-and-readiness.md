# 测试前置条件与阻塞说明（T4）

## 1. 背景

- T1（需求澄清）结果显示：用户仅发送问候语“你好”，未提供任何可验证的功能需求、质量需求、约束或验收标准。
- T2（设计）因需求缺失未能产出真实架构设计、接口定义与任务分解，仅交付《设计前置条件与阻塞说明》。
- T3（实现）因设计缺失未能实现任何业务功能模块，仅交付《实现前置条件与阻塞说明》与一个不依赖业务需求的占位健康检查模块 `src/health.py`。
- T4（测试）依赖 T3。由于 T3 未产出真实业务实现，T4 无法编写覆盖真实功能、边界与异常场景的测试用例，也无法对业务实现进行验证。

## 2. 阻塞结论

**T4 当前被需求缺失阻塞。** 在缺少已确认功能需求、接口定义与验收标准的情况下，任何“业务功能测试用例”都将是虚构的，无法与用户预期对齐，且无法客观判定通过与否。

本任务不产出虚构的业务测试用例，仅产出：

1. 本阻塞说明文档；
2. 针对现有占位健康检查模块的真实可运行测试（`tests/test_health.py`），用于验证工程骨架可用。

## 3. 测试启动所需的最小输入集

| 编号 | 输入项 | 说明 | 来源 |
| --- | --- | --- | --- |
| I1 | 功能需求清单 | 每条需求可验证、可编号 | 用户 |
| I2 | 验收标准 | 每条需求对应的通过/失败判定条件 | 用户 |
| I3 | 接口定义 | 模块边界、输入输出、错误码 | T2 设计文档 |
| I4 | 可运行实现 | 与接口定义一致的业务代码 | T3 实现 |
| I5 | 非功能指标 | 性能、并发、安全等可量化阈值（如有） | 用户 |

## 4. 测试启动条件（全部满足方可解除阻塞）

1. I1 与 I2 已由用户确认，且无“待定/占位”条目；
2. I3 已随需求确认更新，接口签名与错误语义明确；
3. I4 已提交且可在本地无外部依赖地运行；
4. I5 若存在，已给出可量化阈值与测量方法。

## 5. 需求确认后可立即套用的测试流程

1. **需求映射**：将每条功能需求映射到至少一个测试用例 ID，建立需求-用例追溯矩阵。
2. **用例设计**：对每条需求设计正常路径、边界值、异常路径三类用例。
3. **用例编写**：按 `tests/test_<module>.py` 命名，使用 pytest 组织，用例名体现需求编号。
4. **执行与记录**：执行全部用例，记录通过/失败/跳过数量与失败详情。
5. **缺陷登记**：失败用例登记为缺陷，附最小复现步骤、期望结果、实际结果。
6. **回归验证**：缺陷修复后重跑相关用例与全量用例。
7. **验收判定**：全部验收标准对应用例通过，且无未关闭的高优先级缺陷，方可交付。
